# 跨网盘复制与订阅跨盘补源——通用能力设计

日期：2026-10-18 ｜ 定稿一：范围 / 传输模式 / 补源策略 / 源形态；定稿二（2026-10-18）：**扩展为通用能力**——任意网盘之间均可互相搜索与复制，115↔夸克仅为首发组合

## 1. 背景与目标

用户的主力播放库在 **115 网盘**（付费容量大、播放画质与带宽好），但 115 对每周更新的动漫/剧集命中通常比 **夸克网盘** 晚一天左右；夸克资源全、更新快，但高速下载与播放体验差，目前只当作"资源雷达 + 暂存"。

现状痛点：115 订阅任务命中慢 → 手动用 OpenList 的复制功能把夸克里的资源搬到 115 → 再靠文件夹监控生成 `.strm` 播放。整个跨盘搬运依赖手工。

目标（通用化表述）：在项目内建"**任意网盘任务可搜索其他网盘、并把资源保存到本网盘**"的通用能力，并与影视订阅打通——订阅任务在自家候选缺失或更差时，自动把其他网盘候选复制进本网盘目录，后续监控 / STRM / 刮削链路完全复用。115↔夸克是用户当前痛点的**首发组合**，但架构、字段、UI 全部按通用设计，不绑定具体网盘；新增网盘组合只是补 provider 能力 + 勾选配置。

地基工作：项目当前所有网盘均无上传/秒传能力（§3.1），先补上**各网盘的内置上传能力**，再建跨盘复制与互传。

本文档在 8 月两份历史文档（`2026-08-25-cross-cloud-transfer-feasibility.md`、`2026-08-27-cross-cloud-copy-design.md`，均未落地）的基础上，结合新一轮调研重新收敛方案。

## 2. 需求理解（工作流复盘）

```
【现状】（以 115 为例，其他网盘同理）
TG/PanSou 搜索 ──► 115 订阅任务（provider=115）──► 115 分享转存 ──► 监控刷新 ──► STRM ──► 播放
                └─► 夸克订阅任务（provider=quark）──► 夸克保存（暂存）
                                                          │
                                        手动 OpenList 复制 │（当前瓶颈）
                                                          ▼
                                                     115 网盘 ──► 监控刷新 ──► STRM

【期望】（任意网盘任务通用）
订阅任务搜索时附加"其他网盘补源"候选：
  · 自家候选优先（分享转存 / 磁力离线，服务端完成，最快）
  · 自家没有或更差时，选中其他网盘候选 ──► 自动跨盘复制（源分享/网盘 → 本网盘目录）
  · 复制完成 ──► 复用现有监控刷新链路（STRM + 自动刮削）
```

用户自己已识别的两个技术点，本次调研给出的结论：

- **"一边上传一边下载、不占本地磁盘"（纯流式）**：技术上可做（有界队列管道），但与"秒传优先"存在根本冲突——秒传判断需要**完整 SHA1**，而 SHA1 只有读完整文件才能算出；不缓冲全文就算不出来。坚持纯流式只有两条路：放弃秒传直接上传（丢掉"通常秒传"的最大收益），或缓冲全文再传（即退化为方案 C）。因此纯流式不适合作为默认路径。
- **"先完整下载到本地再上传"**：方向正确，且有一个关键优化——**下载一遍的同时计算 SHA1，先试秒传；命中则零上传**（用户已观察到 115 秒传命中率高）。未命中才从本地临时文件分片上传。

**推荐方案（C）＝ 单遍流式下载 + 同步哈希 + 秒传优先 + 临时文件兜底上传**：

```
源网盘直链 ──► 流式读取（一边读一边算 SHA1 + MD5）
                │
                ├─ 小文件（≤ 内存阈值，默认 64MB）→ 内存缓冲，不落盘
                └─ 大文件 → 写临时文件（持久卷，完成后即删）
                ▼
         目标网盘秒传（115：initupload 只需 SHA1+大小+文件名；夸克：md5+sha1 双哈希；阿里：content_hash）
                │
                ├─ 命中 → 删除缓冲 → 完成（下载一遍、上传零次）
                └─ 未命中 → 分片上传（可断点续传）→ 回调完成
```

**定稿（2026-10-18）**：采用方案 C；**纯流式边下边传（方案 B）不做**（用户决策：实现难度与收益不匹配——秒传优先场景下流式一旦未命中反而要 2× 下载）。

**通用化定稿（2026-10-18，定稿二）**：跨网盘搜索/复制对**所有网盘**开放，不限 115；某条"源→目标"组合能否使用由**能力矩阵**决定（§3.4），UI/API/订阅表单按能力动态启用或禁用；首发落地组合仍为夸克→115。

## 3. 调研结论

### 3.1 项目现状盘点（代码侧）

| 能力 | 115 | 夸克 | 天翼 | 123 | 阿里 |
|---|---|---|---|---|---|
| 分享转存 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 同盘复制/移动/重命名/删除 | ✅ | ✅ | ✅ | 部分 | ✅ |
| 离线下载（磁力/ed2k/URL） | ✅ lixian | ❌ | ❌ | ❌ | ❌ |
| 源盘下载直链 | ❌（routes/strm.py 内有 RSA 下载解析，未提升到 provider） | ❌ | ❌ | ❌ | ❌ |
| 目标盘上传 / 秒传 | ❌ | ❌ | ❌ | ❌ | ❌ |
| 文件夹监控 / STRM | ✅ | ❌ | ❌ | ❌ | ❌ |

- 订阅任务按 `provider_filter` 过滤候选（`core.py: search_resource_sources`），任务只会拿到自家 provider 的分享/磁力候选——这是"补源"要打通的第一个点。
- 资源导入任务体系成熟：`resource_jobs` 表 + 创建/取消/重试/进度/任务中心接口齐备，跨盘复制任务可直接复用（老设计同结论）。
- 8 月老设计（只做流式中转、不做秒传、入口在刮削页、范围 115/阿里/夸克两两互传）**未落地**，代码中无任何 `cross_cloud` 痕迹。
- **监控/STRM 目前仅 115 具备** → 非 115 目标复制完成后的"自动刷新"收口暂缺，见 §4.5。

### 3.2 外部技术调研

**（1）115 上传/秒传栈（目标侧，有成熟 Python 参考实现）**

链路（参考 `p115client` / `p115oss` 0.1.2，纯 Python，PyPI 可查）：

1. `GET https://uplb.115.com/3.0/getuploadinfo.php` → 上传 endpoint + token 地址；
2. `GET https://uplb.115.com/3.0/gettoken.php` → 阿里云 OSS STS 令牌；
3. `POST https://uplb.115.com/4.0/initupload.php` → **秒传初始化**。载荷含 `userid`、`userkey`、`fileid`（完整 SHA1）、`filename`、`filesize`、`target`（`U_1_<目标cid>`）；**请求体需 ECDH + AES 加密**（独立小包 `p115cipher` 实现，依赖 `ecdsa`/`pycryptodome`，可借鉴或 vendor）。秒传命中返回 `reuse=true`；未命中返回 OSS 上传参数（bucket/object/callback）；
4. OSS 分片上传（默认 10MB/片，STS 签名 URL PUT，分片 etag 汇总）→ 带 callback 完成；
5. `POST https://uplb.115.com/3.0/resumeupload.php` → 凭 pickcode 断点续传（`list_parts` 算已传偏移）。

- `userkey` 来自 `GET https://proapi.115.com/app/uploadinfo`（cookie 换取，可缓存）。
- 老 3.0 `initupload.php` 接口另需"前 128KB SHA1（preid）"+ 本地算 sig；4.0 接口不再需要 preid。优先按 4.0 实现，保留 3.0 作兜底研究。
- 限流：秒传接口被限流返回 HTTP 405，需退避。
- 账号若开启二次验证，init 可能返回 status 7 要求按 `SignCheck` 字节段现算摘要（`115driver` 有参考实现）——风险项，见 §6。

**（2）夸克下载直链（源侧）**

- 分享文件：`POST https://drive-pc.quark.cn/1/clouddrive/share/sharepage/download`，body `{fids, pwd_id, stoken, share_fid_tokens}` → `data.download_url`；
- 个人网盘文件：`POST https://drive-pc.quark.cn/1/clouddrive/file/download`，body `{fids}`；
- 直链特性（多个独立来源一致）：**有时效（分钟级～1 小时）**；请求方需携带 **UA（夸克 PC 版）+ Referer（必须是具体分享页 URL）**，部分场景还要 Cookie（`_uid`/`_sid`）；**支持 Range**；CDN 多运营商分发热门；非付费账号限速。

**（3）已排除的方案：目标盘服务端离线下载（115 lixian 代下夸克直链）**

115 lixian（`add_task_url`）虽然接受任意 URL，但夸克直链绑 UA/Referer/Cookie、时效短、可能绑 IP，115 服务端无法携带这些凭据 → **不可行**。跨盘搬运必须经过本机（或项目服务器）中转。

**（4）夸克上传/秒传（P0-A 上传能力内置的一部分）**

链路已在多个在维护的开源 driver 中确认（OpenList `quark_uc` driver、alist 分支代码）：

1. `POST /1/clouddrive/file/upload/pre`（`file_name`/`size`/`pdir_fid`/`format_type`）→ 返回 `task_id`、bucket/obj_key/upload_id、`part_size`、callback；
2. `POST /1/clouddrive/file/update/hash`（`md5` + `sha1` + `task_id`）→ **`finish=true` 即秒传命中**。注意：夸克秒传要 **MD5 + SHA1 双哈希**，管道单遍读取时需同时计算两个（MD5 成本可忽略）；
3. 未命中：`POST /1/clouddrive/file/upload/auth`（逐片取 OSS 签名）→ PUT 分片 → `POST /1/clouddrive/file/upload/commit`（分片 md5 汇总 + callback）。

- 8 月可行性文档记录过"社区反馈接口失效"，但当前开源 driver 仍在使用，**排期后需真实账号小文件实测校准**；
- OpenList 官方文档明确注明：**夸克因限速问题，传输只能走本地代理**（服务端先下载再转发）——反向印证本设计"下载到本地再上传"是夸克生态下唯一稳定路线。

**（5）跨盘秒传矩阵（哈希体系决定）**

- 115 ↔ 阿里云盘：均 SHA1，且阿里 API 可直接读 `content_hash` → **阿里→115 可零流量秒传**（用户已确认使用阿里，列入 P1）；
- 115 → 阿里：项目已有 `get_115_file_sha1_by_id`（`pan115.py:301`，经 `webapi.115.com/files/get_info` 的 `sha` 字段直查）→ **同样可零流量秒传**；该字段对"新导出文件"的稳定性已在现网使用，P1 首次实测确认对普通转存文件同样稳定即可（成本一次小文件验证）；
- 夸克 ↔ 115：**夸克 API 不暴露文件 SHA1**，必须读完整文件才能算哈希 → 无零流量路径，只能"下载一遍 + 秒传尝试"；
- 天翼/123：整文件 MD5 体系，与 115 不互通。

**（6）业界先例**

- `cloud-auto-save-x`（FastAPI+Vue，与本项目同栈）：自研复制引擎，流式/下载两种模式、分片并发、**秒传数据自动沉淀**（复制成功后留哈希，复分发时零下载）；
- OpenList 跨 driver copy：本地代理流式 + 各 driver 秒传尝试（其 115 driver Put 即先 rapidUpload 再 OSS 分片）；
- 两者都验证了"下载一遍 + 秒传优先 + 未命中分片上传"是当前网盘生态下的最优工程解。

**（7）"不保存、直接下载分享"的机制与限制（决策点 4 的调研依据）**

- 机制：分享页 token 接口取 `stoken` → `share/sharepage/download`（传分享文件 fid + stoken）→ CDN 直链（支持 Range）。**不转存也能下**，链路本身可通；
- 限制（2026 年社区实测资料）：
  - **限速**：非付费/低权限账号分享直下被服务端 QoS 限速（约 100KB/s–1MB/s，随账号权限/时段/文件类型浮动；连接数压制 + TCP 窗口收缩，与本地网络无关）；付费账号从**自己网盘**下载走高速通道（VIP 约 10MB/s，SVIP 满速），但**分享链下载同样可能被限速**；
  - **次数**：免费账号转存有年限（约 300 次/年）；分享直下亦有次数上限的社区反馈；
  - **时效与验证**：分享链常 7 天过期；大文件直下可能触发验证码或被要求先保存；
- 结论：**订阅补源默认"先转存到源网盘 → 从自己网盘下载"**——转存是服务端秒级操作、不耗本地流量；自己盘内下载走账号权益、速度稳定；彻底绕开分享直下的限速/次数/验证/过期四类风险。分享直下保留为可选模式（小文件、不想占源盘空间时用）。

**（8）阿里云盘上传/秒传要点（P1 互传的目标侧，来自阿里 PDS 官方文档）**

- 秒传：创建文件时传 `content_hash`（完整 SHA1）+ `content_hash_name="sha1"`，Domain 级去重，**命中即完成、零流量**；官方另支持"预秒传"（前 1KB 哈希预判，提前终止无谓的完整哈希计算）；
- 未命中：响应给 `part_info_list`，**固定 10MB/片**（实测，2026-10-18 修正：此前记录的 4MB 有误），向 `upload_url` **PUT 裸字节（不带任何额外 header）**，再 complete；断点续传以 part 为粒度，上传窗口 10 天（超期需重新 create）；
- 创建文件需 `proof_code`（RSA-SHA256 签名，`proof_version=v1`，官方 Web 端同款算法，社区有参考实现）——P1 实现重点与风险点；
- 配额满返回 `QuotaExhausted`；
- **阿里文件列表 API 直接返回 `content_hash`（SHA1）** → 阿里→115 可"读哈希直接秒传、零流量"，无需下载。

### 3.3 候选方案比选

| 方案 | 磁盘 | 带宽成本 | 秒传利用 | 复杂度 | 结论 |
|---|---|---|---|---|---|
| A. 目标盘离线（lixian 代下） | 零 | 零（服务端） | 不涉及 | 低 | **不可行**（直链绑凭据） |
| B. 纯流式边下边传 | 零 | 1×下载+1×上传 | 放弃秒传，或缓冲全文后退化为 C | 中 | **不做**（2026-10-18 决策） |
| C. 临时文件中转 + 秒传优先 | 峰值=单文件大小 | 1×下载 + 0~1×上传 | 充分 | 中高 | **推荐（默认）** |
| D. 委托 OpenList API 完成 | 依赖 OpenList | 同 C | 依赖其 driver | 低 | 保留为可选后端，不作主路径 |

### 3.4 源×目标能力矩阵（通用化的约束）

| 源 \ 目标 | 115 | 夸克 | 阿里 | 123 | 天翼 |
|---|---|---|---|---|---|
| **夸克** | — | **P0-B** | **P0-B** | P2 | P2 |
| **阿里** | **P1**（零流量秒传优先） | **P1** | — | P2 | P2 |
| **115** | — | **P1** | **P1**（零流量秒传，`get_115_file_sha1_by_id`） | P2 | P2 |
| **123** | P2 | P2 | P2 | — | P2 |
| **天翼** | P2 | P2 | P2 | P2 | — |

- **组合可用条件**：源具备 `resolve_download_url`（下载直链）**且**目标具备上传/秒传（`rapid_upload` 等）。任一不满足 → UI 禁用并提示"能力建设中"；
- **哈希体系**：115/阿里 = SHA1 秒传；夸克 = MD5+SHA1 双哈希秒传；123/天翼 = MD5 体系。管道单遍同时算 SHA1+MD5，故三家目标的秒传全都覆盖；**零流量秒传**仅当源 API 直接暴露哈希时成立（当前仅阿里 `content_hash`）；
- **监控刷新收口**目前仅 115 目标支持（文件夹监控/STRM 为 115 独有）；其他目标复制完成即终态，日志注明"目标网盘暂无监控，跳过刷新"；
- **P0-A + P0-B 完成后开通**：夸克→{115, 阿里}——即任意 provider ∈ {115, 阿里} 的订阅任务均可把夸克加入「源网盘」列表（夸克任务自身不能再选夸克，源≠目标）；
- **P1 完成后**：115/夸克/阿里三家两两互通（6 个组合）。

### 4.2 Provider 接口扩展（`app/providers/base.py`）

沿用 8 月老设计的命名并补充秒传钩子：

```python
supports_transfer_source: bool = False   # 可作复制源（提供下载直链）
supports_transfer_target: bool = False   # 可作复制目标（提供上传/秒传）

# 源侧
def resolve_download_url(self, cookie, file_id, entry=None, context=None) -> Dict:
    """返回 {url, headers, supports_range, name, size}。
    context 携带分享上下文（夸克：pwd_id/stoken/fid_token）。"""

# 目标侧
def rapid_upload(self, cookie, target_id, filename, size, sha1, md5=None, context=None) -> Dict:
    """秒传尝试。返回 {ok, file_id?, upload_params?}；ok=False 时 upload_params 供普通上传。"""

def create_upload_session(self, cookie, target_id, filename, size, part_size, upload_params) -> Dict: ...
def upload_part(self, cookie, session, part_number, data) -> Dict: ...
def complete_upload(self, cookie, session, parts) -> Dict: ...
def abort_upload(self, cookie, session) -> None: ...
def resume_upload(self, cookie, session) -> Dict: ...   # 可选，断点续传
```

- 所有请求继续遵守现有 `throttle()` / `mark_cookie_health_*` 约定；直链、签名参数、userkey 不得写日志。
- `supports_transfer_source` / `supports_transfer_target` 由各 provider 按实现进度声明，**UI、API 校验、订阅表单均以此判断某条"源→目标"组合是否可用**（§3.4 矩阵即由这两个标志推导）；
- P0-A 实现上传（目标侧）能力：**115 / 夸克 / 阿里**三家（覆盖已确认的全部场景）；**123/天翼的上传接口预留、实现排 P2**。源侧 P0-B 先实现夸克，P1 补阿里（下载直链）与 115（从 `routes/strm.py` 提取 RSA 下载逻辑）。

### 4.3 115 目标侧实现要点（`app/providers/pan115.py` + 新文件）

- 新增 `app/providers/pan115_cipher.py`：ECDH(P-256) + AES 加解密，参考 `p115cipher` 0.0.6 实现（依赖 `ecdsa` 或 `pycryptodome`，二选一，进 `requirements.txt`）。
- `rapid_upload`：`uploadinfo`（user_id/userkey，缓存 TTL）→ `4.0/initupload.php`（加密载荷）→ `reuse=true` 即命中，返回 pickcode；未命中返回 OSS 参数。

- 断点续传：`3.0/resumeupload.php` + `list_parts` 计算已传偏移；重试任务优先续传，失败才整文件重来。
- 完成后校验：按 name+size 回查目标目录；可选 `get_115_file_sha1_by_id` 校验 SHA1（默认开启，成本一次列表/详情调用）。

### 4.4 夸克源侧实现要点（`app/providers/quark.py`）

- `resolve_download_url`：
  - 分享源：复用现有 `_request_quark_share_token` / stoken 体系，POST `share/sharepage/download`（`fids` + `share_fid_tokens`）→ download_url；headers 带 cookie + 夸克 PC UA + 分享页 Referer；
  - 网盘源：POST `file/download`（`fids`）→ download_url；
- 直链短时效：**每次重试必须重新取链**（不在任务里缓存 URL）；下载中 403/410 视为链接失效，自动换链重试一次。
- 限速感知：连续失败退避；单任务默认串行，避免风控。

### 4.5 复制服务（新增 `app/services/cross_cloud_copy.py`，provider 无关）

**清单构建**

- 源条目为文件 → 直接入清单；为目录 → 递归 `list_entries` 展开，`rel_path` 保持相对目标目录的层级；
- 清单项 `{rel_path, name, file_id, size, is_dir, source_ref}`，`source_ref` 记录分享上下文或网盘 fid；
- 构建阶段只建目录、不传数据；目标目录用目标 provider 的 ensure folder 能力（115 已有，其他 provider 补齐）。

**单文件管道**（`_copy_single_file`）

1. `resolve_download_url` 取直链（失败重试 2 次，间隔退避）；
2. 流式读取（`requests` stream，优先 Range）：单遍同时喂 **SHA1 + MD5** hasher（夸克秒传要双哈希）；前 128KB 单独哈希备用（115 3.0 接口兜底）；
3. 写入 sink：`size ≤ cross_copy_memory_threshold_mb`（默认 64MB）→ 内存 `BytesIO`；否则写临时文件 `{temp_dir}/<job_id>/<idx>__<name>`；
4. `rapid_upload`：命中 → 删 sink → 完成；未命中 → 从 sink 分片上传（`create_upload_session` → `upload_part` × N → `complete_upload`）；
5. 校验（name+size，可选 SHA1）→ 清理 sink；
6. 取消检查点在每个分片边界：上传中取消 → 调 `abort_upload` 清理会话，任务标记 failed 并注明"已取消"。两种结局要说清：**abort 成功** → 无残留，重试 = 整个文件重新开始；**abort 失败**（如网络已断）→ 可能残留未完成分片，重试时按 `resume_upload` 续传。取消确认框文案与此保持一致（见 §4.11-D）。

**任务编排**（`run_cross_cloud_copy_job`）

- 读 `job.extra`：`source_provider` / `target_provider` / `source_mode` / `source_entries` / `target_path` / `target_cid` / `monitor_task_names`；
- 提交校验：源≠目标；源具备下载直链能力；目标具备上传能力（§3.4）；
- 逐文件执行，进度节流写入（默认 2s）：`跨盘复制：3/10 个文件 · 电影/01.mkv（45%）`；
- 全部完成 → `status=completed` → 目标具备监控能力时（当前仅 115）尝试触发刷新（STRM + 自动刮削）。区分两种"跳过刷新"：① 目标网盘暂无监控能力（非 115）→ 终态 + 日志；② 目标是 115 但目录未被任何监控任务覆盖 → 同样跳过，提示语为"目录未配置监控，STRM/刮削需手动触发"；
- 失败 → `status=failed` + 明确明细；重试复用现有 `/resource/jobs/retry`（整文件重来，有 resume 信息时续传）。注意：**内存通道的小文件无断点续传**（进程重启内存即释放），重试 = 重新下载；断点续传仅对临时文件通道的大文件生效。

**并发与磁盘治理**

- 全局信号量限制同时复制任务数（默认 1，可配），保护家庭宽带与两侧风控；
- 临时目录默认 `/app/config/cross_copy_tmp`（跟随 config 卷，Docker 用户无需额外挂载）；
- 孤儿清理：启动时 + 每 30 分钟清理超过 24 小时的残留临时文件（仿 `subscription_offline_cleanup.py`）；
- 复制前幂等检查：目标目录已存在同名同大小文件 → 跳过并记日志（防重复提交）；
- 订阅场景的任务层去重：订阅每轮扫描可能反复命中同一候选，需在订阅侧记录"该候选已发起补源"（task × candidate 维度），避免每轮重复创建复制任务；复制任务内的幂等检查兜底（详见 §4.7 执行链路第 6 步）。
- 复制前空间预检：临时目录所在卷剩余空间 < 待复制文件大小 → 任务直接失败并提示（避免下到一半磁盘满）。

**存储位置管理（`local_storages`，2026-10-18 新增）**

容器通常跑在固态上，而跨盘复制的暂存文件是大块顺序写，落机械硬盘更合理（SSD 磨损 + 容量）。但 Docker 容器外的任何主机路径都必须 bind mount 进来才能用——没有捷径。为此提供一层「存储位置」抽象，用户不用手改路径字符串：

- 设置页维护位置列表：`[{id, label, path}]`，默认一条 `{id: "config", label: "默认（config 卷）", path: "/app/config"}`；
- 添加/编辑位置时校验：路径存在、可写（`os.access(W_OK)`）、`shutil.disk_usage` 可读；任一不满足给出明确错误，不允许保存；
- `cross_copy_temp_dir` 的 UI 从"填路径"改为"选位置 + 填子目录"（如位置 `storage` + 子目录 `cross_copy_tmp`），存储时合成完整路径；保留高级模式可直接填任意路径；
- 设置页与任务中心展示各位置剩余空间（`shutil.disk_usage`）；复制任务详情显示本次使用的存储位置；
- 位置被卸载/硬盘弹出时：任务失败并明确报错（不静默无限重试），孤儿清理兜底。

> 适用范围说明：项目其他本地写入都很小——STRM 是几 KB 的文本文件、日志、SQLite、图片代理缓存（默认 32MB 上限），唯一的大块本地磁盘消耗就是跨盘复制暂存。因此「存储位置」首先服务 `cross_copy_temp_dir`；接口按通用设计，未来的本地缓存/离线下载保存位置可直接复用同一套位置管理。

### 4.6 任务接入（2026-10-18 已落地：独立表 `cross_copy_jobs`）

实现时放弃"复用 `resource_jobs`"，改为独立任务表——原因：`resource_jobs` 与 magnet/share 导入语义强耦合（`resource_id NOT NULL`、`run_resource_job` 按 link_type 分发），跨盘复制任务没有 resource 项，复用会污染资源导入链路。项目本身存在多任务表模式（`scraper_jobs` / `tree_export_jobs` / `monitor_runs`），跨盘复制遵循同一模式：

- 表 `cross_copy_jobs`（`app/db.py`）：标题、源/目标 provider、`source_file_id`、`source_share_url`（save_first 去重键）、`source_mode`（direct / save_first）、目标目录/路径、文件名/大小、状态机（pending → running → completed / failed / cancelled / skipped）、进度（percent + phase + status_detail）、`origin`（manual / subscription）+ `origin_ref`（订阅任务名）、重试计数；
- service `app/services/cross_copy_jobs.py`：创建 / 查询 / 取消（内存取消集合 + DB 双保险）/ 重试（整任务重来）/ 启动恢复（`requeue_cross_copy_jobs_on_startup`，重启残留任务重新入队）/ 进度上报 / 完成与失败通知（`cross_copy_notify` 开关控制）；
- 路由 `app/routes/cross_copy.py`：`GET /cross_copy/capabilities`（源×目标矩阵，UI 置灰依据）、任务列表/详情、`POST /cross_copy/jobs`（手动入口）、`/cancel`、`/retry`；
- 前端任务中心页面接入（网盘浏览"复制到 <目标网盘>"按钮）随 UI 迭代补齐，API 已就绪。

### 4.7 订阅集成（跨盘补源，所有任务类型通用）

**任务新字段**（`normalize_subscription_task` 扩展，不限 provider）：

- `cross_copy_mode`：`"off"`（默认，保持现状）| `"fallback"`（自家候选缺失或明显更差时用其他网盘候选）| `"prefer"`（其他网盘候选优先）；
- `cross_copy_sources`：其他网盘名列表，**默认排除任务自身 provider**，仅可勾选已实现下载直链能力的网盘（P0 仅夸克可选，P1 加阿里/115）。

术语约定：「**跨盘补源**」指本功能本身；`cross_copy_sources` 的 UI 标签为「**源网盘**」（复制的来源方），任务自己的网盘称「**目标网盘**」。连用时写作"跨盘补源的源网盘"，不造"补源网盘""补源源"这类叠词或歧义短语。

**执行链路（2026-10-18 已落地，`app/services/subscription_task_runner.py` 候选就绪处 + `app/services/subscription_cross_copy.py`）**：

1. 字段已进 `normalize_subscription_task`：`cross_copy_mode`（off/fallback/prefer）+ `cross_copy_sources`（源网盘白名单：当前仅 quark；自动排除任务自身 provider）；
2. 订阅候选就序后（不动原有候选尝试循环）：`cross_copy_mode != off` 且 sources 含夸克时，从候选中挑夸克分享（按评分降序、去重、单轮上限 3 个）走 **save_first**：`resolve_share_payload` → `list_share_entries` → 转存到夸克专属中转目录 `云下载/跨盘中转/<任务名>` → 列目录按「文件名 + 大小」匹配拿 fid → 创建 `cross_copy_jobs`（origin=subscription, origin_ref=任务名, source_share_url=分享链接）；
3. **fallback 语义由幂等跳过保证**（不判断导入结果，避免在巨型候选循环里加分支）：订阅转存成功 → 文件已在目标盘 → 补源任务 `check_existing` 命中跳过；转存失败/未命中 → 补源任务把资源复制进目标网盘；
4. 异步收尾：注册后订阅本轮即继续（不等待复制），订阅日志写"跨盘补源已入队：夸克 → <目标>（文件，任务 #id）"；失败明细透出不静默；
5. 去重：同一订阅任务（origin_ref）+ 同一分享链接（source_share_url）已有 pending/running 任务时跳过（DB 查询），防每轮重复注册；
6. 删源安全边界：复制成功后只删中转目录内本任务记录的 file_id（`cross_copy_delete_source_after` 默认开），绝不按文件名全局删。

**可用性校验**（表单 + API 两层）：

- 任务 provider 需具备上传能力，否则"跨盘补源"分组禁用并提示"该网盘上传能力建设中"；
- `cross_copy_sources` 中的网盘需具备下载直链能力；
- 源≠目标（自家 provider 不出现在可选列表）。

> **源形态定稿（2026-10-18）**：订阅自动补源默认 **`save_first`（先转存到源网盘 → 从自己网盘下载 → 秒传/上传目标）**。理由见 §3.2(7)：转存是服务端秒级操作、不耗本地流量；自己盘内下载走会员权益、稳定；彻底避开分享直下的限速/次数/验证/过期风险；且订阅链路本来就要执行"保存到网盘"（fallback 时保存目标由自家盘切换为源网盘），复用现有逻辑改动最小。
>
> - `share_direct`（分享直下）保留为可选模式：适合小文件、不想占源盘空间的场景；大文件不建议（限速 + 验证风险）；
> - 手动入口同时支持**网盘源**（源网盘里已存的文件，同样是先下载再秒传/上传）；
> - 新增「复制成功后源文件处理」配置（默认**删除**转存到源网盘的临时文件，节省空间；可改为保留）。**安全边界**：`save_first` 的转存必须落到源网盘的**专属中转目录**（复用订阅磁力离线同款 staging 模式——`SUBSCRIPTION_OFFLINE_STAGING_ROOT`，subscription_task_runner.py:27），删除只删该目录内本次任务记录的文件 id，**绝不按文件名全局匹配删除**，避免误删用户自有文件；

### 4.10 部署说明（compose 挂载）

当前 `compose.yml` 的三个挂载（strm / logs / config）都在 Docker 数据目录（通常是 SSD）。要把跨盘复制暂存放到机械硬盘，只需再加一个 bind mount，并在设置页把存储位置指过去：

```yaml
services:
  115-media-hub:
    build: .
    container_name: 115-media-hub
    volumes:
      - /Users/xianer/Documents/docker/115strmxianer/strm:/app/strm
      - /Users/xianer/Documents/docker/115strmxianer/logs:/app/logs
      - /Users/xianer/Documents/docker/115strmxianer/config:/app/config
      # 额外存储（跨盘复制暂存区用；按需改为你的机械硬盘/NAS 路径，不映射则暂存落在 config 卷）
      - /Volumes/media:/app/storage
    ports:
      - "18080:18080"
    environment:
      - TZ=Asia/Shanghai
    restart: always
```

设置页 → 存储位置 → 添加 `{label: "机械硬盘", path: "/app/storage"}` → 跨盘复制设置里临时目录选该位置 + 子目录 `cross_copy_tmp`。label 是给人看的（“机械硬盘”“NAS 仓库”随意写），容器内路径保持中立——挂的到底是什么盘由 label 表达，不与路径耦合。

- 有多块额外磁盘就挂多个（`/app/storage`、`/app/storage2`……），在设置页分别添加位置，复制时按需选；
- macOS Docker Desktop 首次访问外部卷会弹权限授权，需允许；
- NAS（NFS/SMB）同理：先在主机挂好，再 bind 进容器；
- 硬盘卸载/弹出时位置校验失败，任务明确报错，不会写坏盘。

### 4.11 界面提示与用户引导（2026-10-18 补）

原则：**跨盘复制是"看不见的后台搬运"，每一态都要让用户知道发生了什么、要等多久、失败了怎么办**。按触点梳理：

**A. 设置页（参数配置）**

- "跨盘复制"分组顶部一句定位说明 + "查看文档"链接（README 锚点）；
- 每项配置问号 tooltip（内容即 §4.9 说明列，并标注是否热生效——均热生效，无需重启）；
- `cross_copy_delete_source_after` 开启时配**警告样式**："开启后，复制成功的文件会从源网盘删除（仅删本项目转存/复制产生的临时文件）"——涉及删除用户文件，必须醒目；
- 存储位置：添加/保存失败时错误文案明确（路径不存在 / 不可写 / 读不到容量三种分别提示）；列表展示 label + path + 剩余空间；

**B. 订阅任务表单（"跨盘补源"分组）**

- 开关旁一句话解释语义："自家网盘命中就不复制；只有没命中或更差时，才从源网盘复制（比同盘转存慢，但更新快）"；

- 模式 radio 三个人话说明：`off`=关闭；`fallback`=兜底（推荐）；`prefer`=优先跨盘（更新最快，但每次命中都要复制一遍）；
- 当 `cross_copy_delete_source_after=true` 时，表单内提示"复制成功后源网盘文件将被删除"；
- 保存后 toast："已开启跨盘补源，每次补源结果可在任务页查看"。

**C. 手动入口（刮削页/网盘浏览"复制到 <目标>"）**

- 确认框展示：源 → 目标、条目数/总大小、暂存位置及所需空间（不足时直接禁用提交并提示）、是否删除源文件、当前取数模式；

- 源/目标能力不可用时入口置灰 + 原因 tooltip。

**D. 任务中心（复制任务）**

- 状态机的人话映射：排队 → 取直链 → 下载（x%）→ 秒传尝试 → 上传（x%）→ 校验 → 完成；每态一行说明（如"秒传尝试：命中则零上传，通常几秒"）；

## 5. 决策定稿（2026-10-18）

| # | 决策点 | 定稿 | 理由 |
|---|---|---|---|
| 1 | **P0 范围** | 先给网盘补上**内置上传能力**（统一抽象 + 115/夸克/阿里实现）；先落地「下载到本地再上传」的普通复制（夸克→115）；随后做**阿里↔115 互传** | 上传能力是所有跨盘复制的地基；用户的真实场景就是这两条链路 |
| 2 | **传输模式** | 大文件 → **本地磁盘中转**，支持秒传就启用秒传；小文件（≤64MB）→ **内存缓冲**；**纯流式不做** | 用户决策；流式与秒传根本冲突且未命中时 2× 下载，收益不抵复杂度 |
| 3 | **补源策略** | `fallback`：先搜索筛选，**自家有（且不差）就不复制**；只有自家没有/更差而其他盘有，才跨盘复制 | 用户决策；同盘转存/离线始终最快最稳，跨盘复制是兜底 |
| 4 | **源形态** | 默认 `save_first`（先转存源网盘再下载）；`share_direct` 可选；复制成功后**默认删除源文件** | 分享直下有限速/次数/验证/过期四类风险（§3.2(7)）；转存 + 自己盘内高速下载稳定且不耗本地流量 |
| 5 | **通用能力化**（定稿二） | 跨网盘搜索/复制对**所有网盘**开放，不限 115；组合可用性由能力矩阵（§3.4）驱动，UI/API/表单按 `supports_transfer_source/target` 动态启用禁用；首发落地组合仍为夸克→115 | 用户决策：其他网盘也要支持跨网盘搜索；架构全通用，新增组合只是补 provider 能力 + 勾选配置 |

默认按上表推进，可随时调整的两个非阻塞项：

- 123/天翼的上传实现是否提前（当前建议留 P2，接口层已预留，补实现不影响主线）；
- 阿里 `proof_code` 与「115→阿里」的 SHA1 获取方式，P1 动手前先做小文件技术探针。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 115 initupload 为逆向接口且请求体 ECDH 加密 | 实现成本高、易随官方变更失效 | 参考 p115cipher/p115oss 成熟实现；先以真实账号小文件校准；保留 3.0 老接口作备援研究 |
| 115 账号开启二次验证（status 7 需按字节段算摘要） | 秒传/上传初始化失败 | 实现 SignCheck 摘要逻辑（115driver 有参考）；探测到即引导用户临时关闭或降级 |
| 夸克直链绑 UA/Referer/Cookie、时效短 | 下载中途 403/410 | 换链重试；失败任务重试时重新取链；不在任务内缓存 URL |
| **夸克秒传检测的哈希大小写** | 大写 sha1 在"云端已有该文件"时 400 `invalid file [sha1 非法]`，复制必失败 | 2026-10-20 真机定位：`update/hash` 的 md5/sha1 **必须小写**；已修并加回归用例。教训：这类"只在命中时才报错"的接口只能靠真机发现 |
| 夸克账号下载限速（用户为 88VIP 赠送的低档会员，实际速度档位待实测）+ 风控 | 复制慢、账号风险 | 默认串行 + 退避；任务可配时段（复用订阅调度窗口）；频率可视化 |
| **夸克分享直下被限速/次数限制** | 复制慢或直接失败 | 默认 `save_first` 转存模式绕开；`share_direct` 仅建议小文件 |
| 115 秒传 405 限流 | 连续失败 | 指数退避 + 单任务串行；批量复制每 N 个暂停 |
| 阿里 `proof_code`（RSA-SHA256）逆向变更 | 创建文件/秒传失败 | 参考社区成熟实现；P1 先以小文件实测校准；失败明确报错不静默 |
| 临时文件占磁盘 | 磁盘打满 | 阈值可配 + 孤儿清理 + 完成即删 + 任务中心展示临时目录占用 |
| 秒传命中率不稳定 | 未命中时上传慢 | 属预期内（慢但成功）；P2 引入哈希沉淀缓存减少重复下载 |
| **非 115 目标无监控刷新** | 复制完成后不自动刮削 | 当前仅 115 有监控/STRM；完成即终态并明确日志。**2026-10-20 决策：改为「不做」，不再等监控扩展**——非 115 目标没有监控目录可作为意图依据，猜错就会把用户已整理好的结构二次搬走；手动入口保留在「文件管理」页 |
| **存储位置未挂载/被卸载** | 任务失败或写入报错 | 位置保存时校验存在+可写；任务开始前复检；失败明确报错不静默重试；孤儿清理兜底 |
| **暂存卷空间不足** | 下到一半磁盘满、任务卡死 | 复制前空间预检（剩余 < 文件大小即失败）；设置页展示剩余空间；孤儿清理 |
| 123/天翼上传逆向成本高 | 排期膨胀 | 接口层预留、实现排 P2，当前场景不涉及 |
| 接口变更维护成本 | 长期 | 集中在 provider 层；cookie 健康体系已具备监控能力 |

> - **修掉真机 bug：夸克秒传检测的 sha1 必须小写**。`POST /1/clouddrive/file/update/hash` 传大写 sha1 时，若云端已存在同一文件会直接 400 `invalid file [sha1 非法]`；同一请求改成小写立刻 200 且 `finish=true`。未命中时它不校验大小写，所以单测与小文件都"看起来正常"，只有「115 → 夸克，且夸克已有这个文件」才会炸——这正是 `196 4K.mp4`（2.61GB）那条任务失败的原因。改动：`_quark_upload_hash` 的 md5/sha1 统一转小写；新增回归用例 `test_hash_payload_always_lowercase`。

## 9. 未覆盖 / 后续评估

- **任务记录管理**：已于 2026-10-20 补齐（批量清空 + 单条删除 + 按条数自动裁剪），口径见 §7 第三批；表本身因此不再无限增长。
- 123/天翼的上传与作为源（整文件 MD5 哈希体系，上传侧逆向成本高，排 P2）；用户 2026-10-20 明确「这两个盘现在不用」，暂不排期。
- 上传的**分片级重试**已于 2026-10-20 落地（见 `2026-10-20-upload-part-retry.md`）：
  三家 provider 的分片失败只重发那一片，不再退回整文件重传；
  **跨进程续传**（重启后接着 uploadId 传）仍未做，`supports_upload_resume` 语义不变；
- **单任务内并行分段下载**：现在是 16MB 一段、串行请求（实测 9~10MB/s）。要再快就得每段独立哈希再按序合并，收益与复杂度都要再评估。
- 非 115 目标的监控/STRM（复制完成后的自动刮削）：**已决策不做**，理由见 §7 P2。
- 115→阿里方向的零流量秒传：项目已有 `get_115_file_sha1_by_id`，真机实测一次确认 `sha` 字段对普通文件的稳定性后即可定稿；注意阿里秒传前要读 `pre_hash`，即使哈希可信仍会触发一次下载。
- 纯流式边下边传：**明确不做**（2026-10-18 用户决策，见 §5）；
- 服务器中转（把家庭宽带换成 VPS 转发）——本机带宽瓶颈的终极解法，但引入信任与成本问题；
- 与 OpenList 的双向集成（本项目为主、OpenList 兜底）。
